# Optional HTTP transports and destination routing

`Source.js` can expose VLESS XHTTP (`stream-one`), VLESS/Trojan gRPC
(`Hunk` framing), and destination-based selection between an account's
configured upstreams. Existing WebSocket subscriptions remain available.
These additions use the same users, protocol permissions, expiry checks
and traffic counters as the WebSocket engine; they do not introduce
a separate account database.

## Enable features

Deploy `Source.js` with the existing `DB` binding. Add the following Worker
variables only for the features you want:

| Variable | Enabled value | Default |
| --- | --- | --- |
| `HTTP_TRANSPORTS` | `true` (string or boolean) | Disabled |
| `SMART_ROUTING` | `true` (string or boolean) | Disabled |

Refresh the existing `/feed/<username>` or `/yaml/<username>` subscription.
HTTP profiles use TLS port 443 independently of the account's WebSocket port
list. Smart adds a distinct `loc-auto` option; numbered `loc-N` options keep
their manual meaning. Smart requires at least one valid country-labelled
upstream configured on that account.

Use a Cloudflare custom domain with gRPC enabled for native gRPC clients.
Client support for XHTTP and gRPC varies: select `stream-one` for this XHTTP
implementation and single-stream `Tun`/Hunk for gRPC. `stream-up`,
`packet-up`, multi-gRPC, raw UDP VPN servers and Shadowsocks over HTTP are
not implemented here. HTTP/3 support at the edge does not imply raw UDP
forwarding by this Worker.

The existing browser **Copy Config** generators and dashboard configuration
counts describe the WebSocket profiles. The text/YAML subscription endpoints
are the authoritative exports for the optional profiles. Branding, informational
subscription entries, attribution and upstream deployment/version files remain
unchanged. `zeus.obfuscated.js` is not regenerated by this source-only proposal;
maintainers should use their release process before distributing a new release.

## Account upstreams

Configure upstreams through the existing user proxy setting. Its stored JSON
form is, for example:

```json
[
  { "country": "DE", "proxy": "socks5://USER:PASSWORD@exit.example.invalid:1080" },
  { "country": "US", "proxy": "wss://REPLACE_WITH_TOKEN@relay.example.invalid/tcp-relay" }
]
```

Values above are placeholders. Keep real credentials in the account's protected
configuration; do not commit them or publish them in issue reports. The private
WebSocket upstream sends its token as an Authorization header after removing
it from the request URL. It requires HTTPS and the relay protocol documented in
[`examples/wss-relay`](../examples/wss-relay/README.md). It is independent of
any country, host provider or container runtime.

## Smart policy and privacy

Smart first applies known service rules and conservative country-code domain
hints. Otherwise it resolves the hostname through Cloudflare DNS-over-HTTPS,
then asks `api.country.is` for the hosting country of a public IP. DNS receives
the destination hostname; the country API receives the resolved IP. No HTTPS
body is decrypted, and no private destination IP is sent to the country API.
Do not enable this option if those external metadata lookups are unsuitable.

A hosting country is a routing hint, not proof of a site's owner or the best
route. Anycast/CDN addresses may not identify a single meaningful country.
Known AI domains prefer the configured US/DE/GB/CA/TR/AE exits; this is a
best-effort access policy, not a guarantee that a particular service accepts
the selected IP. Smart does not measure throughput or select the fastest ISP
route.

Only upstreams already assigned to the account are eligible. Positive and
negative resolver results and recent failures have bounded caches; in-flight
network work is request-owned. There are at most three sequential upstream
handshake attempts, each with a three-second budget. After one handshake
succeeds, application bytes are sent once. A later application failure is
not replayed through a different exit. Smart does not silently add a direct
fallback or discover unrelated public proxies.

## Streaming and resource limits

The HTTP adapter waits for the original protocol engine to authenticate the
account and check its quota before producing a successful tunnel response.
Uploads await protocol processing and downloads respect bounded backpressure.
Cancellation closes late/outstanding upstream sockets and releases capacity.

Current conservative per-isolate HTTP bounds are 16 concurrent tunnels,
64 KiB chunks, a 128 KiB soft output queue, a 2 MiB hard output queue, a
1 MiB gRPC frame limit, a 10-second authentication deadline and a 180-second
idle/drain timeout. These are application bounds, not account-wide Cloudflare
limits. Quota accounting continues to use the existing Zeus buffering model;
this change does not claim globally synchronous accounting across isolates.
The upstream engine's disabled IP-limit checks are unchanged; this proposal
does not add enforcement for those settings.

The optional WSS upstream has bounded queues, a 10-second upgrade deadline
and a 15-second acknowledgment deadline. The relay acknowledges upload bytes
only after draining them to TCP. This bounds memory but can constrain upload
throughput on a high-latency path; it is not a throughput optimization claim.

## Validation and rollout

With Node.js 22 or newer:

```sh
npm test
```

The Worker suite uses synthetic identities, mock D1 and mock sockets. It tests
fragmented protocol headers, authentication/expiry/quota rejection, exact
payload framing, queue limits, cancellation, Smart fallback/no replay, manual
route preservation, feature flags and subscription output. It does not access
production accounts or the Internet. See the relay README for Python tests.

First enable the variables on a staging Worker with a test account. Verify
each enabled transport with a supported real client on the intended network,
then verify subscription output and traffic accounting. Disable the variables
to reject the corresponding new ingress routes and omit their subscription
nodes. Active connections are not retroactively terminated by a variable
change. Manual WebSocket routes remain available.

Do not infer performance from a protocol name or an edge-IP ping. Compare the
same destination, client interface and upstream, measuring setup, warm request
latency and complete download time separately. Avoid running a benchmark
inside another active system VPN. HTTP/2 probe receive windows must be large
enough for the bandwidth-delay product; a default 65,535-byte window can make
a custom probe the bottleneck.

References: [Workers protocols](https://developers.cloudflare.com/workers/reference/protocols/),
[Xray XHTTP](https://github.com/XTLS/Xray-core/discussions/4113),
[Node HTTP/2 flow control](https://nodejs.org/api/http2.html#http2sessionsetlocalwindowsizewindowsize).


## Connection setup and subscription preferences

Text and YAML exports list Smart profiles first, then keep each configured
country's transports together. Route indices and account credentials are preserved.
VLESS/Trojan WebSocket exports advertise up to 2560 bytes of early data through
`Sec-WebSocket-Protocol`. The server bounds and validates that header, then uses
the same ordered authentication and quota-checking queue as ordinary WS frames.
Clients without early data remain supported; Shadowsocks export is unchanged.

Append `?profile=compact` to a feed/YAML URL to export port 443, the first
configured edge IP, and one already-enabled protocol (VLESS, then Trojan, then
Shadowsocks). It retains configured country routes and enabled HTTP transports.
Append `&client=standard` (or `?client=standard` by itself) to omit custom
fragmentation, cipher and TLS-mask export parameters. Neither option changes
stored account settings, usage or expiry. These are opt-in client preferences,
not measured performance guarantees.

Five lookup indexes match UUID, username and Trojan hash collations, including
an exact 12-hex-character UUID suffix lookup for Shadowsocks. Legacy account
backfills use a persistent settings marker committed in the same D1 batch, so
later cold isolates do not repeatedly scan the users table. A failed transaction
is retried on a later isolate. These optimizations do not increase D1 quotas or
immediately restore a database that has already exhausted its daily allowance.
Run `python tests/test-d1-query-plans.py` to verify the real index definitions
against SQLite query plans with synthetic records.
